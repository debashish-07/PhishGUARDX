# PhishGuardX Storage Requirements (Academic Version)

Version: 1.1  
Date: April 17, 2026

---

## Overview

PhishGuardX uses a simple local storage design that matches a final-year project implementation. The system stores recent detection results in a JSON ledger, keeps the trained model file on disk, and reads configuration from local files.

The goal is clarity and reliability for moderate usage, not enterprise-scale deployment.

---

## 1. Storage Components

### 1.1 Local Ledger

- File: backend/data/ledger.json
- Format: JSON Lines (one detection record per line)
- Role: Keeps recent detection history for review and explainability
- Access pattern: Append new entries, read recent entries

Each record contains:
- URL hash and timestamp
- Final label (safe, suspicious, phishing)
- Risk score and confidence
- Reasons generated by the detection pipeline
- Feature signals used in scoring

### 1.2 Model File

- File: backend/models/phishguard_v1.0.pkl
- Format: Pickle (scikit-learn RandomForest)
- Role: Loaded at startup and reused for inference

### 1.3 Configuration Files

- Directory: backend/config/
- Typical files:
  - trust_policy.yaml
  - thresholds.yaml
  - rules.yaml
- Role: Keeps project settings readable and easy to update

### 1.4 Optional Local Cache

- Backend: Redis (optional)
- Use case: Faster repeated checks for same URL in demos/tests
- If not enabled, system still works correctly with file-based ledger only

## 2. Practical Capacity Statement

The system is designed to handle moderate usage efficiently. Each detection entry is lightweight, and the ledger stores recent results.

For the project context:
- Typical runs: class demos, testing scripts, small batch evaluations
- Suitable for thousands of checks during testing
- Local disk usage remains manageable for academic workflows

---

## 3. Performance Statement

Detection is fast, with model inference completing in under a second, making it suitable for real-time use.

In practice, total response time includes:
- Feature extraction
- Hybrid scoring (ML + heuristic + HTTPS)
- Explainability generation
- Ledger append

This keeps user feedback immediate in API and demo usage.

---

## 4. Storage Behavior

The system maintains a local ledger for recent detections and can be extended with archiving if needed.

Current behavior:
- Append detection records to ledger.json
- Query recent records through API endpoint
- Keep storage local and easy to inspect during viva

Optional extension (future work):
- Periodically move old records to a local archive file
- Compress archive if ledger grows over long-term use

---

## 5. Data Integrity and Safety

### 5.1 Integrity

- Ledger uses hash-linked records for auditability
- Each new entry references the previous record
- Chain checks can detect accidental tampering

### 5.2 Operational Safety

- Keep a copy of ledger.json before major experiments
- Keep one previous model file before replacing model version
- Validate model loading after updates

These simple practices are enough for final-year project reliability.
